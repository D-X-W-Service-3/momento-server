# 기술 선택 기록이 남는 이슈 / PR 작성

목적은 두 가지다.

1. **리뷰어가 판단할 수 있게** — 코드가 아니라 선택을 리뷰할 수 있어야 한다.
2. **작성자가 나중에 설명할 수 있게** — 몇 달 뒤 면접이나 회고에서 "왜 그렇게 했나요"에
   근거를 대며 답할 수 있는 수준으로 남긴다. 이게 이 스킬의 핵심이다.

그래서 "프론트가 SDK 를 쓰니까 이 방식으로 했다" 같은 한 줄 요약은 실패다.
**어떤 방식들이 존재하는지 → 각각 어떻게 동작하는지 → 우리 기준으로 평가하면 어떤지 →
그래서 무엇을 골랐고 무엇을 포기했는지** 까지 가야 한다.

## 모드

| 입력 | 동작 |
|---|---|
| `/git issue` | 앞으로 할 작업을 이슈 본문으로 작성. 구현 전이므로 **인터뷰(2단계)가 중심**이다 |
| `/git pr` | 현재 브랜치 작업을 PR 본문으로 작성. 코드에서 사실을 모으고(1단계) 빈칸만 인터뷰로 채운다 |
| 인자 없음 | `git log develop..HEAD` 에 커밋이 있으면 PR, 없으면 이슈로 본다 |

---

## 1. 먼저 사실을 모은다 (사용자에게 묻기 전에)

PR:
```bash
git log --oneline develop..HEAD
git log develop..HEAD --format='%B'      # 커밋 본문에 이유가 적혀 있는 경우가 많다
git diff develop...HEAD --stat
git diff develop...HEAD
```

이슈: 관련 기존 코드, `application.yml`, `CLAUDE.md` 의 제약, 이미 있는 도메인 패키지 구조를 읽는다.

**여기서 확인되는 것은 절대 다시 묻지 않는다.** 인터뷰는 코드에 없는 것만 묻는 자리다.
"Redis 쓰나요?" 같은 질문을 사람에게 던지지 말고 `build.gradle` 과 `application.yml` 을 먼저 본다.

## 2. 인터뷰 — 부족한 것을 질문으로 끌어낸다

`/git issue` 에서는 이 단계가 본체다. 작성자가 "카카오 로그인 만들 거야" 한 줄만 던져도
아래를 채워 이슈가 나와야 한다. `/git pr` 에서는 코드로 안 드러나는 "왜"만 골라 묻는다.

### 질문 방식

- **AskUserQuestion 으로 한 번에 3~4개씩 묶어서** 묻는다. 한 개씩 여러 번 왕복하지 않는다
- 매 질문에 **선택지를 제시**한다. 백지 서술형으로 던지면 답이 부실해진다
- **"아직 모름"도 유효한 답**으로 받는다. 모른다고 하면 그 항목은 본문에 `> 확인 필요:` 로 남기고 넘어간다.
  모르는 걸 캐물어 진행을 막지 않는다
- 인터뷰는 **최대 2라운드**. 그 이상 물으면 팀원이 스킬을 안 쓴다

### 물을 것

1. **완료 기준** — 이 작업이 끝나면 누가 무엇을 할 수 있게 되나. 사용자 관점 한 문장
2. **클라이언트 구성** — 웹 / 앱 / 둘 다. (인증·업로드·알림 계열에서 방식 비교의 핵심 축이 된다)
3. **제약** — 외부 연동 대상, 이번에 확정 안 된 것(ERD, AI 서버 스펙 등), 일정상 마지노선
4. **알고 있는 구현 후보** — "생각해 둔 방식이 있는지". 없으면 아래 흐름으로 간다
5. **이번에 안 할 것** — 스코프 경계. 이슈가 커지는 걸 여기서 막는다

1~3 은 코드·CLAUDE.md 에서 상당 부분 채워지므로, 실제로 묻는 건 보통 2, 4, 5 다.

### 후보를 모른다고 하면 — 여기가 이 스킬의 핵심

절대 "그럼 제가 알아서 하겠습니다" 로 넘어가지 않는다. 대신:

1. 그 기능의 구현 방식을 **2~4개 조사해서 제시**한다 (흐름 3~5줄 + 우리 기준에서 갈리는 지점)
2. **어떤 기준에서 갈리는지**를 같이 보여준다 — "앱까지 지원해야 하면 A 가 불리하다" 식으로
3. 그 상태에서 **작성자가 고르게** 한다. 스킬이 대신 결론을 내지 않는다

모르는 사람이 골라도 근거를 갖게 되는 것이 목표다. 아는 사람만 잘 쓰는 스킬이면 실패다.
작성자가 "추천해달라"고 하면 추천하되, 추천의 근거를 우리 제약과 연결해서 말하고
본문에는 "제안받아 채택" 이라는 사실을 남긴다.

### 인터뷰 종료

답을 모아 **한 문단으로 요약해 확인받고** 본문 작성으로 넘어간다.
여기서 어긋나면 이슈를 다 쓴 뒤 갈아엎는 것보다 싸다.

## 3. 이번 작업의 "결정 축"을 뽑는다

한 작업에 결정이 여러 개일 수 있다. 소셜 로그인 하나에도
`카카오 인증 흐름` / `자체 토큰 전략(단일 vs access+refresh)` / `탈퇴 회원 처리` 가 각각 결정이다.

결정으로 다룰 것:
- 같은 목표를 이루는 방식이 둘 이상 실재한다
- 나중에 바꾸는 비용이 크다 (API 스펙, DB 스키마, 외부 연동 프로토콜, 토큰 정책)
- 팀 컨벤션이나 일반적인 관행에서 벗어난다

오타·포맷·리네이밍은 결정이 아니다. 이런 작업은 기술 선택 섹션 없이 짧게 쓴다.
결정 축이 3개를 넘으면 가장 중요한 1~2개만 깊게 쓰고 나머지는 한 줄로 넘긴다.
얕은 정리 5개보다 깊은 정리 1개가 목적에 맞다.

## 4. 방식들을 조사한다

각 결정 축마다, **그 기능을 구현할 수 있는 방식을 빠짐없이** 적는다.
우리가 검토했든 안 했든 업계에서 통용되는 선택지는 모두 올린다 (보통 2~4개).

방식마다 채울 것:

- **흐름** — 누가 무엇을 호출하고 무엇을 받는지 순서대로.
  프론트 / 우리 서버 / 외부 서버 중 누가 무엇을 하는지가 드러나야 한다
- **서버가 해야 하는 일** — 보관할 값(시크릿, 토큰), 필요한 엔드포인트, 필요한 설정
- **장점**
- **약점 / 비용**

모르는 API 스펙이나 라이브러리 동작은 추측하지 말고 코드·문서로 확인하거나 `> 확인 필요:` 로 표시한다.
인터뷰에서 작성자가 "검토 안 했다"고 한 방식을 검토한 것처럼 쓰지 않는다.

## 5. 우리 기준으로 평가한다 — 여기가 제일 중요하다

일반론("성능이 좋다", "많이 쓴다")은 근거가 아니다.
**우리 서비스의 요구사항과 제약에서 평가 기준을 먼저 뽑고**, 그 기준으로 표를 만든다.

기준을 뽑을 때 볼 것:
- 클라이언트 구성 (웹 SPA / 앱 / 둘 다, 프론트가 이미 쓰는 SDK)
- 우리 아키텍처 규칙 (`Controller → Facade → Service → Repository`, `CommonResponse`, 예외 체계)
- 인프라·운영 (배포 환경, 관리할 시크릿, 서버 상태 보관 여부, DB/스토리지 유무)
- 팀·일정 (Backend 4 / Frontend 3 / AI 4, 다른 팀과의 연동 지점)
- 확정되지 않은 것 (ERD, AI 서버 엔드포인트 등)

```
| 기준 (왜 이 기준인지) | 방식 A | 방식 B | 방식 C |
|---|---|---|---|
| ... | ... | ... | ... |
```

○△✕ 만 찍지 말고 칸마다 이유를 한 구절로 적는다.

## 6. 선택과 트레이드오프

- **선택**: 어떤 방식을, 어떤 기준 때문에 골랐는지. 기준 표의 행을 지목하며 쓴다
- **포기한 것**: 이 선택으로 못 하게 된 것을 구체적으로.
  "단점 없음" 은 쓰지 않는다. 없으면 애초에 결정 축이 아니었던 것이다
- **재검토 조건**: 어떤 상황이 오면 다시 볼지 (예: "앱에서 카카오 refresh token 이 필요해지면")
- **이 선택이 강제하는 것**: 이 방식을 고른 이상 반드시 해야 하는 일과 그 코드 위치

이슈(구현 전)라면 결론을 확정하지 않아도 된다. 다만 **어느 쪽으로 왜 기우는지,
무엇이 확인되면 확정되는지**는 적는다.

## 7. 남겨 둘 학습 포인트

마지막에 **"짚고 갈 것"** 섹션을 둔다. 이번 작업에서 알게 된 것, 리뷰어가 물을 만한 것,
나중에 설명해야 할 것을 질문–답 형태로 3개 내외. 빈칸 채우기가 아니라 실제로 나온 것만 쓴다.

## 8. 확인 후 등록

초안은 스크래치패드에 파일로 쓰고 대화에 보여준다. **사용자 승인 전에는 등록하지 않는다.**

```bash
gh issue create --title "..." --body-file <초안>
gh pr create --base develop --title "..." --body-file <초안>
gh pr edit <번호> --body-file <초안>     # 이미 열린 PR
```

이슈 번호·브랜치는 작성자가 직접 만드는 경우가 많으니 먼저 물어보고 시키는 대로 한다.
`gh` 로그인이 안 돼 있으면 초안 파일 경로를 알려주고 거기서 멈춘다.

## 형식 규칙

- 한국어, `~다` 체. 제목은 커밋 컨벤션과 같은 `<type>: <제목>` (`CONTRIBUTING.md`)
- 저장소의 `.github/pull_request_template.md`, `.github/ISSUE_TEMPLATE/` 섹션은 그대로 두고
  **기술 선택 섹션을 덧붙인다**. 기존 템플릿을 지우지 않는다
- 코드 위치는 `AuthController.java:22` 형태로 짚는다
- 표는 GitHub 마크다운 표. 흐름 설명은 번호 목록이나 코드블록 시퀀스

세부 틀은 `references/templates.md`,
실제 작성 예시는 `references/example-kakao-login.md` (이 저장소의 카카오 로그인 기준).
