# 기술 선택 기록이 남는 이슈 / PR 작성

목적은 두 가지다.

1. **리뷰어가 판단할 수 있게** — 코드가 아니라 선택을 리뷰할 수 있어야 한다.
2. **작성자가 나중에 설명할 수 있게** — 몇 달 뒤 면접이나 회고에서 "왜 그렇게 했나요"에
   근거를 대며 답할 수 있는 수준으로 남긴다. 이게 이 스킬의 핵심이다.

"프론트가 SDK 를 쓰니까 이 방식으로 했다" 같은 한 줄 요약은 실패다.

## 모드 — 이슈와 PR 은 담는 것이 다르다

같은 내용을 두 번 쓰지 않는다.

| | `/git issue` (구현 전) | `/git pr` (구현 후) |
|---|---|---|
| 무게중심 | **무엇을 왜 지금 하는가** + 결정 사항과 근거 + 구현자가 알아야 할 함정 | **실제로 고른 방식과 대안 비교** + 트레이드오프 |
| 방식 비교표 | 넣지 않는다. 결정별로 서술해 압축한다 | 넣는다. 기준별 표로 견준다 |
| 근거의 출처 | 저장소 조사(2단계) + 인터뷰(3단계) | 코드·커밋(1단계) |
| 검증 | "완료 기준" 으로 미리 정의 | 실제로 확인한 결과 |

인자가 없으면 `git log develop..HEAD` 에 커밋이 있으면 PR, 없으면 이슈로 본다.

## 1. 사실부터 모은다 (사용자에게 묻기 전에)

PR:
```bash
git log --oneline develop..HEAD
git log develop..HEAD --format='%B'      # 커밋 본문에 이유가 적혀 있는 경우가 많다
git diff develop...HEAD --stat
git diff develop...HEAD
```

이슈: 관련 기존 코드, `build.gradle`, `application.yml`, `CLAUDE.md`, `CONTRIBUTING.md`,
`.github/` 를 읽는다.

**여기서 확인되는 것은 절대 다시 묻지 않는다.**
"Redis 쓰나요?" 를 사람에게 묻지 말고 `build.gradle` 을 먼저 본다.

## 2. 저장소를 조사해 "지금 왜 문제인가"의 근거를 만든다 — 이슈의 값은 여기서 나온다

느낌으로 쓰지 않는다. **숫자와 경로로** 쓴다.

- "포맷 규칙이 없다" ✕ → "`.editorconfig` 가 없고 `coding-style.md` 에도 규정이 없다. Java 파일 34개" ○
- "확장성이 나쁘다" ✕ → "지금은 인원이 적어 안 드러나지만, 늘면 IDE 설정 차이로 공백만 바뀐 diff 가 섞인다" ○

```bash
find src -name '*.java' | wc -l        # 규모
ls .github/workflows                    # 있다고 알려진 것이 실제로 있는지
```

### 전제 검증 — 이걸 찾아내는 게 가장 큰 값이다

작업의 전제가 실제로 성립하는지 확인한다. 자주 깨지는 것들:

- 문서에 적힌 것이 실제로 없다 (CI 게이트가 문서에만 있고 `.github/workflows` 가 없다)
- 이 작업만으로는 효과가 안 난다 (검사를 붙여도 강제할 CI 가 없어 로컬에서만 동작)
- 머지 전에 사람이 해야 할 일이 있다 (IDE 플러그인 설치, 환경변수 주입, 세션 재시작)

발견하면 본문 **"⚠️ 짚고 갈 것"** 에 쓰고, 필요하면 후속 이슈가 필요하다고 명시한다.
문제를 감추지 말고 드러낸다.

## 3. 인터뷰 — 부족한 것을 질문으로 끌어낸다

`/git issue` 에서는 이 단계가 본체다. 작성자가 "카카오 로그인 만들 거야" 한 줄만 던져도
이슈가 나와야 한다. `/git pr` 에서는 코드로 안 드러나는 "왜"만 골라 묻는다.

### 질문 방식

- **AskUserQuestion 으로 한 번에 3~4개씩 묶어서** 묻는다. 한 개씩 왕복하지 않는다
- 매 질문에 **선택지를 제시**한다. 백지 서술형으로 던지면 답이 부실해진다
- **"아직 모름"도 유효한 답**으로 받는다. 그 항목은 `> 확인 필요:` 로 남기고 넘어간다
- 인터뷰는 **최대 2라운드**. 그 이상 물으면 팀원이 스킬을 안 쓴다

### 물을 것

1. **완료 기준** — 끝나면 무엇이 검증 가능해지는가. "~가 통과한다", "~하면 실패한다"
2. **클라이언트 구성** — 웹 / 앱 / 둘 다 (인증·업로드·알림에서 방식이 갈리는 축)
3. **제약** — 외부 연동, 확정 안 된 것(ERD, AI 서버 스펙), 일정
4. **알고 있는 구현 후보** — 없으면 아래 흐름으로
5. **이번에 안 할 것** — 스코프 경계. 본문의 "이번 범위에서 제외한 것" 이 된다

1~3 은 2단계에서 상당 부분 채워지므로 실제로 묻는 건 보통 2, 4, 5 다.

### 후보를 모른다고 하면 — 이 스킬의 핵심

"그럼 제가 알아서 하겠습니다" 로 넘어가지 않는다.

1. 그 기능의 구현 방식을 **2~4개 조사해 제시**한다 (흐름 3~5줄 + 우리 기준에서 갈리는 지점)
2. **어떤 기준에서 갈리는지** 보여준다 — "앱까지 지원해야 하면 A 가 불리하다"
3. 그 상태에서 **작성자가 고르게** 한다

모르는 사람이 골라도 근거를 갖게 되는 것이 목표다. 아는 사람만 잘 쓰는 스킬이면 실패다.
추천을 요청받으면 추천하되 근거를 우리 제약과 연결하고, 본문에 "제안받아 채택" 이라고 남긴다.

### 인터뷰 종료

답을 한 문단으로 요약해 확인받고 본문 작성으로 넘어간다.

## 4. 결정 축을 뽑는다

한 작업에 결정이 여러 개일 수 있다. 소셜 로그인 하나에도
`카카오 인증 흐름` / `자체 토큰 전략` / `탈퇴 회원 처리` 가 각각 결정이다.

결정으로 다룰 것:
- 같은 목표를 이루는 방식이 둘 이상 실재한다
- 나중에 바꾸는 비용이 크다 (API 스펙, DB 스키마, 외부 연동 프로토콜, 토큰 정책)
- 팀 컨벤션이나 관행에서 벗어난다

오타·포맷·리네이밍은 결정이 아니다. 결정 축이 3개를 넘으면 중요한 1~2개만 깊게 쓰고
나머지는 한 줄로 넘긴다. 얕은 정리 5개보다 깊은 정리 1개가 목적에 맞다.

## 5. 결정을 쓴다 — 이슈는 서술, PR 은 비교표

### 이슈: 결정마다 대안의 장점을 먼저 인정하고 시작한다

```
### 2. ratchet 대신 전체 일괄 포맷

<대안이 무엇이고 왜 매력적인지 먼저 쓴다>
이번엔 쓰지 않기로 했다.
- <우리 상황에서 그 장점이 왜 작은지 — 저장소의 사실로>
- <따라오는 비용>
```

대안을 깎아내리는 게 아니라 **우리 상황에서 저울이 어느 쪽으로 기우는지**를 보인다.
근거는 반드시 2단계에서 확인한 사실이어야 한다.

### PR: 방식들을 나열하고 기준표로 견준다

방식마다 **흐름**(누가 무엇을 호출하는지) · **서버가 해야 하는 일** · **장점** · **약점**.
그다음 **우리 제약에서 뽑은 기준**으로 표를 만든다. 일반론("성능이 좋다")은 근거가 아니다.

기준을 뽑을 때 볼 것: 클라이언트 구성 / 우리 아키텍처 규칙(`Controller → Facade → Service`,
`CommonResponse`, 예외 체계) / 인프라·운영(관리할 시크릿, 상태 보관) / 팀·일정 /
확정되지 않은 것(ERD, AI 서버).

○△✕ 만 찍지 말고 칸마다 이유를 한 구절로 적는다.

## 6. 선택과 트레이드오프

- **선택**: 어떤 기준 때문에 골랐는지
- **포기한 것**: 구체적으로. "단점 없음" 은 쓰지 않는다. 없으면 결정 축이 아니었다
- **재검토 조건**: 어떤 상황이 오면 다시 볼지
- **이 선택이 강제하는 것**: 반드시 해야 하는 일과 그 코드 위치

이슈라면 결론을 확정하지 않아도 된다. 다만 어느 쪽으로 왜 기우는지,
무엇이 확인되면 확정되는지는 적는다.

## 7. 구현자를 위한 메모 (이슈) / 짚고 갈 것 (PR)

이슈에는 **구현 메모** — 구현자가 빠질 함정을 미리 막는다.
따라야 할 기존 패턴("새 패턴을 만들지 않는다"), 커밋을 어떻게 쪼갤지, 참조 방식.

PR에는 **짚고 갈 것** — 리뷰어가 물을 만한 것, 나중에 설명해야 할 것을 Q&A 3개 내외.
빈칸 채우기가 아니라 실제로 나온 것만.

## 8. 확인 후 등록

초안은 스크래치패드에 파일로 쓰고 대화에 보여준다. **사용자 승인 전에는 등록하지 않는다.**

```bash
gh issue create --title "..." --label <type> --body-file <초안>
gh pr create --base develop --title "..." --body-file <초안>
gh issue edit <번호> --body-file <초안>   # 이미 올린 것 수정
gh pr edit <번호> --body-file <초안>
```

이슈 번호·브랜치는 작성자가 직접 만드는 경우가 많으니 먼저 물어보고 시키는 대로 한다.
`gh` 로그인이 안 돼 있으면 초안 파일 경로를 알려주고 거기서 멈춘다.

## 형식 규칙

- 한국어, `~다` 체. 제목은 커밋 컨벤션과 같은 `<type>: <제목>` (`CONTRIBUTING.md`)
- 저장소의 `.github/pull_request_template.md`, `.github/ISSUE_TEMPLATE/` 섹션은 유지하고
  그 위에 섹션을 덧붙인다. 기존 템플릿을 지우지 않는다
- 코드 위치는 `AuthController.java:22`, 문서는 절 번호로 짚는다
- 없던 고민을 지어내지 않는다. 작성자가 검토하지 않았다고 한 방식을 검토한 것처럼 쓰지 않는다.
  확인 안 된 것은 `> 확인 필요:` 로 남긴다

세부 틀은 `references/templates.md`.
작성 예시는 `references/example-issue-spotless.md`(이슈), `references/example-pr-kakao-login.md`(PR).
