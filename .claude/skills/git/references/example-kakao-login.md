## 📝 작업 내용

프론트에서 카카오 SDK 로 받은 액세스 토큰을 `POST /v1/auth/kakao` 로 넘기면,
서버가 카카오에 그 토큰을 검증하며 사용자 정보를 조회하고 가입/로그인 처리한 뒤
서비스 액세스 토큰(JWT)을 발급한다. 신규 가입 여부를 응답에 함께 내려 프론트가
온보딩 화면으로 분기할 수 있다.

- 탈퇴했던 회원이 다시 로그인하면 카카오 프로필로 복구한다
- JWT subject 를 회원 ID 로 잡아, 탈퇴 회원의 토큰은 서명이 유효해도 인증되지 않는다

## 🔍 구현 방식 선택

### 배경 — 우리가 풀어야 했던 것

- 클라이언트는 웹과 앱 **둘 다** 갈 수 있고, 프론트는 이미 카카오 SDK 를 붙일 계획이었다
- 서버는 `Controller → Facade → Service` 흐름에 모든 응답을 `CommonResponse` 로 통일한다.
  인증도 이 흐름 안에 들어와야 예외 처리(`ApiException` + `GlobalExceptionHandler`)가 일관된다
- ERD 가 확정되기 전이라 회원 테이블 컬럼이 흔들리는 상태였다
- 서버는 아직 Redis 같은 별도 저장소가 없다. 상태를 들고 있으려면 DB 뿐이다

### 가능한 방식들

카카오 로그인은 크게 세 가지로 구현할 수 있다. 셋 다 마지막에는 우리 서버가
자체 JWT 를 발급하는 것으로 끝나고, **카카오 액세스 토큰을 누가 받아서 누가 검증하느냐**가 다르다.

#### 방식 A. 백엔드 주도 인가 코드 방식 (서버 리다이렉트)

```
브라우저 → 우리 서버 /oauth2/authorization/kakao
        → 카카오 동의화면
        → redirect_uri(우리 서버 콜백) 로 code 전달
우리 서버 → kauth.kakao.com/oauth/token  (code + client_id + client_secret 교환)
        → kapi.kakao.com/v2/user/me      (사용자 조회)
        → 회원 가입/조회 → 자체 JWT 발급
        → 프론트 페이지로 리다이렉트하며 토큰 전달
```

- 서버가 보관/구현해야 하는 것: 카카오 REST API 키와 client_secret, 환경별 redirect_uri 등록,
  콜백 컨트롤러 또는 Spring Security `oauth2Login` 설정, 성공/실패 핸들러
- 장점: 카카오 액세스 토큰이 클라이언트에 전혀 노출되지 않는다.
  카카오 refresh token 을 서버가 받아 보관할 수 있다. Spring Security 가 흐름 대부분을 대신해준다
- 약점: 리다이렉트 왕복이 전제라 SPA·앱과 잘 안 맞는다. 발급한 JWT 를 프론트에 넘기려면
  쿼리스트링이나 쿠키를 써야 하고, 그 순간 응답이 `CommonResponse` 규약 밖으로 나간다.
  환경(local/prod)마다 redirect_uri 를 카카오 콘솔에 등록해 관리해야 한다

#### 방식 B. 프론트가 인가 코드 수신, 서버가 토큰 교환 (하이브리드)

```
프론트 → 카카오 인증 페이지 (redirect_uri = 프론트 라우트)
      → 프론트가 code 수신
      → POST /v1/auth/kakao { code }
우리 서버 → kauth.kakao.com/oauth/token (code 교환)
        → /v2/user/me → 가입/조회 → JWT 를 JSON 으로 응답
```

- 서버가 보관/구현해야 하는 것: client_secret, redirect_uri(프론트 것과 정확히 일치해야 함),
  토큰 교환 호출
- 장점: client_secret 은 서버에만 있고, 카카오 액세스 토큰도 클라이언트로 가지 않는다.
  응답이 JSON 이라 SPA 와 우리 응답 규약에 맞는다
- 약점: 프론트와 서버가 redirect_uri 를 공유해 관리해야 해서 배포 환경이 늘 때마다 양쪽을 맞춰야 한다.
  네이티브 앱은 SDK 로그인이 자연스러운데 이 방식은 웹 리다이렉트를 다시 끌어와야 한다

#### 방식 C. 프론트 SDK 액세스 토큰 전달 ← 채택

```
프론트 (카카오 JS/Android/iOS SDK) → 카카오 로그인 → 카카오 액세스 토큰 획득
      → POST /v1/auth/kakao { accessToken }
우리 서버 → kapi.kakao.com/v2/user/me  (이 호출 자체가 토큰 검증)
        → 가입/조회 → JWT 를 JSON 으로 응답
```

- 서버가 보관/구현해야 하는 것: 카카오 API 주소뿐. 시크릿도 redirect_uri 도 없다
- 장점: 웹·앱이 같은 엔드포인트 하나를 쓴다. 서버가 카카오 시크릿을 갖지 않는다.
  구현이 컨트롤러 1 + Feign 1 + 서비스 1 로 끝나 우리 계층 규약 안에 그대로 들어온다
- 약점: 카카오 액세스 토큰이 클라이언트에 존재한다. 서버는 전달받은 토큰을
  **절대 그냥 믿으면 안 되고** 반드시 카카오에 물어봐야 한다. 서버가 카카오 refresh token 을
  갖지 못해 카카오 세션 갱신은 프론트 책임이 된다

### 우리 아키텍처 기준 비교

| 기준 (왜 이 기준인지) | A. 서버 리다이렉트 | B. 하이브리드 | C. SDK 토큰 |
|---|---|---|---|
| 웹·앱 동일 API (클라이언트가 둘 다 될 수 있음) | ✕ 앱은 별도 흐름 | △ 앱은 리다이렉트 필요 | ○ 엔드포인트 하나 |
| 응답 규약(`CommonResponse`) 유지 | ✕ 리다이렉트로 토큰 전달 | ○ JSON | ○ JSON |
| 서버가 관리할 시크릿·설정 (운영 부담) | client_secret + redirect_uri | client_secret + redirect_uri | 없음 |
| 환경 추가 시 비용 (local/prod) | 콘솔에 URI 등록 | 콘솔 등록 + 프론트 동기화 | 없음 |
| 카카오 토큰 노출 범위 (보안) | ○ 서버만 | ○ 서버만 | △ 클라이언트에 존재 |
| 카카오 refresh token 보관 | ○ 가능 | ○ 가능 | ✕ 불가 |
| 구현·리뷰 분량 (백엔드 4인, 다른 도메인 병행) | 큼 | 중간 | 작음 |

### 선택: 방식 C

앞 두 행이 결정적이었다. 클라이언트가 웹·앱 둘 다 될 수 있는데 A 는 앱에서 무너지고,
A 는 토큰을 리다이렉트로 넘겨야 해서 모든 API 를 `CommonResponse` 로 통일한다는 규약도 깨진다.
B 는 규약은 지키지만 프론트와 서버가 redirect_uri 를 계속 맞춰야 하는 비용이 남는데,
프론트가 어차피 카카오 SDK 를 붙이는 상황에서 그 비용을 감수할 이유가 없었다.

C 의 약점인 "카카오 토큰이 클라이언트에 있다"는 우리 서비스 범위에서 감당 가능하다고 봤다.
우리가 카카오에서 받는 것은 프로필 정보뿐이고, 그 토큰으로 우리 서비스의 권한을 얻을 수는 없다.
서비스 접근 권한은 어디까지나 우리가 발급한 JWT 로만 생긴다.

실제로 이 선택 때문에 기존에 있던 `oauth2Login` 설정과 리다이렉트 전용 클래스,
카카오 client 설정을 걷어냈다. 카카오 앱 키는 이제 프론트만 사용한다.

### 포기한 것과 재검토 조건

- **포기 1 — 카카오 refresh token**: 서버가 갖지 못하므로 카카오 세션 갱신은 프론트 책임이다.
  서버가 사용자 대신 카카오 API 를 호출해야 하는 기능(예: 카카오톡 메시지 알림)이 생기면
  B 또는 A 로 옮겨야 한다. 알림 도메인 설계 때 다시 본다
- **포기 2 — 카카오 토큰 은닉**: 클라이언트에 카카오 액세스 토큰이 남는다.
  프론트가 이 토큰을 저장소에 오래 두지 않도록 프론트와 합의가 필요하다
- **이 선택이 강제하는 것**: 서버는 넘어온 토큰을 반드시 검증해야 한다.
  `KakaoOAuthService.java:23` 에서 `/v2/user/me` 를 호출하고, 401/403 은
  `INVALID_KAKAO_TOKEN(401)`, 그 외 통신 실패는 `KAKAO_SERVER_ERROR(502)` 로 구분한다
  (`AuthErrorCode.java:11`). 카카오 장애를 사용자 인증 실패로 오해하지 않기 위해 나눴다

### 곁가지 결정 — 서비스 토큰 전략

지금은 **30일 단일 액세스 토큰**이다 (`AuthFacade.java:16`). access + refresh 2종을 두려면
refresh 토큰 저장소가 필요한데 아직 Redis 가 없고 DB 에 넣으면 로그인마다 쓰기가 생긴다.
대신 JWT subject 를 회원 ID 로 두고(`TokenProvider.java:47`) 매 요청마다 회원을 조회하므로,
탈퇴 회원의 토큰은 서명이 유효해도 인증되지 않는다. 만료를 짧게 가져가야 할 시점이나
Redis 가 들어오는 시점에 재검토한다.

## 💡 짚고 갈 것

- **Q. 프론트가 준 액세스 토큰을 그대로 믿으면 왜 안 되나?**
  A. 요청 본문은 누구나 조작할 수 있어서, 검증 없이 신뢰하면 아무 문자열로 남의 계정에
  로그인할 수 있게 된다. 우리는 그 토큰으로 카카오 `/v2/user/me` 를 호출해서,
  카카오가 사용자 정보를 돌려주는 것 자체를 검증으로 쓴다. 토큰이 유효하지 않으면 카카오가 401 을 준다.

- **Q. 그럼 카카오가 200 을 주면 무조건 우리 사용자인가?**
  A. 카카오 토큰은 앱 단위로 발급되므로 다른 앱의 토큰이면 우리 앱 API 호출에서 걸린다.
  더 엄격히 하려면 `/v1/user/access_token_info` 로 `app_id` 가 우리 앱인지 확인하는 방법이 있다.
  지금은 하지 않고 있고, 필요해지면 추가한다.

- **Q. 카카오 서버 오류를 왜 401 이 아니라 502 로 주나?**
  A. 401 은 "네 토큰이 잘못됐다"는 뜻이라 프론트가 재로그인을 유도한다. 카카오가 죽어서 실패한 건
  사용자 잘못이 아니고 재로그인해도 안 풀리므로, 502 로 구분해 프론트가 재시도를 안내하게 했다.
