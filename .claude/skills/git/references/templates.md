# 본문 틀

저장소 기본 템플릿의 섹션은 유지하고, 그 뒤에 기술 선택 섹션을 붙인다.

---

## 이슈 (`/git issue`)

```markdown
## 어떤 기능인가요?

> 한 문단. 사용자 관점에서 무엇이 가능해지는지.

## 📝 작업 상세 내용

- [ ] ...
- [ ] ...

## 🔍 구현 방식 후보

### 방식 A. <이름>

흐름
1. ...
2. ...

- 서버가 해야 할 일: ...
- 장점: ...
- 약점: ...

### 방식 B. <이름>

(동일 구조)

## ⚖️ 우리 서비스 기준 비교

| 기준 (왜 이 기준인지) | A | B |
|---|---|---|
| ... | ... | ... |

## 🎯 현재 기울어진 방향

> 구현 전이므로 결론을 확정하지 않아도 된다. 다만 어느 쪽으로 왜 기우는지,
> 무엇이 확인되면 확정할 수 있는지는 적는다.

## 📁 참고 자료 (선택)
```

---

## PR (`/git pr`)

```markdown
## #️⃣ 연관된 이슈

#번호

## 📝 작업 내용

> diff 를 요약하지 말 것. 이 PR 로 무엇이 가능해졌는지 3~5줄.

- ...

## 🔍 구현 방식 선택

### 배경 — 우리가 풀어야 했던 것

> 이 기능의 요구사항과 제약. 클라이언트 구성, 인프라, 팀, 미확정 사항.

### 가능한 방식들

#### 방식 A. <이름>

흐름
1. ...

- 서버가 보관/구현해야 하는 것: ...
- 장점: ...
- 약점: ...

#### 방식 B. <이름>
#### 방식 C. <이름>

### 우리 아키텍처 기준 비교

| 기준 | A | B | C |
|---|---|---|---|
| ... | ... | ... | ... |

### 선택: 방식 X

> 어떤 기준 때문에 골랐는지. 위 표의 행을 지목하며.

### 포기한 것과 재검토 조건

- 포기: ...
- 이 선택이 강제하는 것: ... (`파일명.java:라인`)
- 재검토: ~하게 되면 다시 본다

## 🧪 검증

- [ ] ...
- 테스트: `SomeTest.java` — 무엇을 보장하는지

## 💡 짚고 갈 것

- **Q. ...?**
  A. ...

## 💬 리뷰 요구사항 (선택)
```

---

## 결정 축이 없는 PR

포맷·오타·설정 정리처럼 선택지가 없었던 작업은 위 틀을 억지로 채우지 않는다.
`연관된 이슈` / `작업 내용` / `검증` 만 쓰고 끝낸다.
없던 고민을 지어내는 것이 이 스킬의 가장 큰 실패다.
