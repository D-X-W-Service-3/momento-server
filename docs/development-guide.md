# Momento 백엔드 개발 가이드

> 코드보다 **판단**을 남기는 개발 방식과, 그걸 돕는 `/git` 스킬 사용법.

---

## 0. 이 문서를 읽기 전에

우리는 지금부터 각자 도메인을 맡아 개발한다. 이때 **가장 쉽게 사라지는 게 "왜 그렇게 했는지"** 다.

코드는 남는다. 커밋도 남는다. 그런데 3주 뒤에 이런 질문을 받으면 대부분 답을 못 한다.

- "이거 왜 Facade 에 뒀어요?"
- "토큰 만료를 왜 30일로 잡았어요?"
- "이미지 업로드를 왜 서버 경유로 했어요? Presigned URL 은 안 봤어요?"

**답을 못 하는 이유는 실력이 없어서가 아니라, 그때 실제로 비교를 안 했거나 비교한 걸 안 적었기 때문이다.**

이 문서와 `/git` 스킬은 그 습관을 강제로 만들기 위한 장치다.

---

## 1. 왜 이 스킬을 만들었나

### 문제

기능을 만들 때 우리는 보통 이렇게 한다.

```
"카카오 로그인 해야 하네" → 구글링 → 블로그 따라 구현 → 동작함 → PR → 머지
```

이러면 **동작하는 코드**는 나온다. 하지만 남는 게 없다.

- 다른 방법이 몇 개나 있었는지 모른다
- 내가 고른 방법의 **약점**을 모른다 (그래서 나중에 터진다)
- 리뷰어는 "코드가 맞나"만 볼 수 있고 "이 선택이 맞나"는 못 본다
- 면접에서 "카카오 로그인 구현했습니다" 이상을 말할 수 없다

### 목표

`/git` 스킬은 딱 세 가지를 강제로 뽑아낸다.

| | 뽑아내는 것 |
|---|---|
| **1** | 구현 **전에** — 무엇을 만들 건지, 끝났다는 걸 어떻게 확인할 건지 |
| **2** | 구현 방법이 **여러 개** 있다는 걸 인지하고, 그것들을 비교하기 |
| **3** | 그중 하나를 고른 **이유**와, 그래서 **포기한 것** |

스킬 문서에 적힌 목적 두 줄이 이거다.

> 1. **리뷰어가 판단할 수 있게** — 코드가 아니라 선택을 리뷰할 수 있어야 한다.
> 2. **작성자가 나중에 설명할 수 있게** — 몇 달 뒤 면접이나 회고에서 "왜 그렇게 했나요"에 근거를 대며 답할 수 있는 수준으로 남긴다.

### 오해하지 말 것

**이건 문서 작업을 늘리려는 게 아니다.** 문서는 부산물이고, 진짜 목적은 **구현 전에 한 번 멈춰서 생각하는 것**이다.

멈춰서 "방법이 이거 말고 또 뭐가 있지?" 를 스스로 묻는 습관. 그게 이 스킬이 만들려는 전부다.
문서는 그 생각을 했다는 증거로 남을 뿐이다.

## 2. 준비물

### Claude Code 설치

각자 설치한다. 설치 후 프로젝트 루트에서 실행한다.

```bash
cd momento-server
claude
```

### 스킬은 따로 받을 필요 없다

스킬은 `.claude/skills/git/` 에 있고 **이미 `develop` 에 커밋돼 있다.**

```bash
git pull origin develop
```

이것만 하면 `/git` 이 바로 잡힌다. `.gitignore` 에서 `.claude/*` 는 제외하되 `!.claude/skills/` 로 스킬만 공유하도록 예외를 뒀다. 개인 설정은 안 올라가고 팀 공용 스킬만 공유된다.

### gh CLI

이슈/PR 을 자동으로 올리려면 필요하다. 없으면 스킬이 초안 파일 경로만 알려주고 멈춘다 (그것도 괜찮다. 복사해서 웹에 붙여넣으면 된다).

```bash
brew install gh
gh auth login
```

## 3. 전체 개발 흐름

```
1. 이슈 작성      /git issue      ← 구현 전에 생각을 정리
2. 이슈 등록      (승인 후 자동)
3. 브랜치 생성    feat/#12-kakao-login
4. 구현           
5. PR 작성        /git pr         ← 고른 방식과 대안을 기록
6. PR 등록        (승인 후 자동)
7. 리뷰 1인 이상 승인 → develop 병합
```

브랜치·커밋 컨벤션은 [`CONTRIBUTING.md`](./CONTRIBUTING.md) 를 따른다. 여기서 반복하지 않는다.

**핵심은 1번과 5번이다.** 이 두 지점에서만 스킬을 쓴다.

## 4. `/git issue` — 구현 전에 쓴다

### 언제

**코드를 한 줄도 안 썼을 때.** 이슈를 만들려는 순간.

### 어떻게

Claude Code 에서 이렇게만 치면 된다.

```
/git issue 카카오 로그인 만들 거야
```

한 줄이어도 된다. 오히려 한 줄로 시작하는 걸 전제로 만들었다.

### 그다음 무슨 일이 일어나나

**1단계 — 저장소를 먼저 읽는다**

Claude 가 `build.gradle`, `application.yml`, `CLAUDE.md`, 기존 코드를 읽는다.
**여기서 알 수 있는 건 너한테 안 묻는다.** "Redis 쓰나요?" 를 사람한테 묻지 않고 `build.gradle` 을 본다.

**2단계 — 질문한다 (최대 2라운드)**

선택지가 딸린 질문 3~4개가 한 번에 온다. 주로 이런 것들이다.

- **완료 기준** — 끝나면 무엇이 검증 가능해지는가
- **클라이언트 구성** — 웹만? 앱도? (인증·업로드·알림에서 방식이 갈리는 축이다)
- **이번에 안 할 것** — 스코프 경계
- **알고 있는 구현 후보**

> **"모르겠는데요" 도 유효한 답이다.**
> 구현 방법 후보를 모르겠다고 하면, Claude 가 **2~4개를 조사해서 흐름과 함께 제시**하고
> **어떤 기준에서 갈리는지**까지 보여준다. 그걸 보고 네가 고르면 된다.
> 스킬 문서에 이렇게 적혀 있다 — *"모르는 사람이 골라도 근거를 갖게 되는 것이 목표다.
> 아는 사람만 잘 쓰는 스킬이면 실패다."*

**3단계 — 초안을 파일로 보여준다**

**승인하기 전엔 절대 등록 안 한다.** 읽어보고 고칠 데 있으면 말하면 된다.

**4단계 — 승인하면 `gh issue create`**

이슈 번호나 브랜치를 네가 직접 만들고 싶으면 그렇게 말하면 된다. 물어보고 시키는 대로 한다.

### 이슈에 담기는 것

| 섹션 | 내용 |
|---|---|
| 어떤 기능인가요? | **저장소에서 확인한 사실로** 쓴 문제 정의 |
| 완료 기준 | "~가 통과한다" 처럼 검증 가능한 문장 |
| 결정 사항과 근거 | 결정마다 **대안의 장점을 먼저 인정**하고 시작 |
| 이번 범위에서 제외한 것 | 스코프가 커지는 걸 여기서 막는다 |
| ⚠️ 짚고 갈 것 | 조사하다 발견한, 전제를 흔드는 사실 |
| 구현 메모 | 구현자가 빠질 함정 |

## 5. `/git pr` — 구현 끝나고 쓴다

### 언제

커밋 다 하고 push 하기 전후. PR 올리려는 순간.

```
/git pr
```

인자 없이 쳐도 된다. `git log develop..HEAD` 에 커밋이 있으면 PR 로, 없으면 이슈로 알아서 판단한다.

### 그다음

**1단계 — 커밋과 diff 를 먼저 읽는다**

```bash
git log develop..HEAD --format='%B'    # 커밋 본문에 이유가 적혀 있는 경우가 많다
git diff develop...HEAD
```

그래서 **커밋 메시지 본문에 "왜"를 써두면 PR 작성이 훨씬 정확해진다.**
`CONTRIBUTING.md` 가 "어떻게(how)보다 왜(why)" 를 쓰라고 한 이유가 여기서도 살아난다.

**2단계 — 코드로 안 드러나는 "왜"만 골라 묻는다**

이슈 때보다 질문이 적다. 이미 코드에 답이 있으니까.

**3단계 — 초안 보여주고, 승인하면 `gh pr create`**

### PR 에 담기는 것 — 이슈와 다르다

**같은 내용을 두 번 쓰지 않는다.**

| | 이슈 (구현 전) | PR (구현 후) |
|---|---|---|
| 무게중심 | 무엇을 왜 지금 하는가 | **실제로 고른 방식과 대안 비교** |
| 방식 비교표 | 안 넣는다 | **넣는다** (기준별 표) |
| 검증 | "완료 기준" 으로 미리 정의 | 실제로 확인한 결과 |

PR 의 핵심은 **비교표**다. 방식마다 흐름 / 서버가 할 일 / 장점 / 약점을 쓰고,
**우리 제약에서 뽑은 기준**으로 표를 만든다.

> ⚠️ 기준은 **우리 것**이어야 한다. "성능이 좋다" 같은 일반론은 근거가 아니다.
> `CommonResponse` 규약을 지키는가 / 웹에서 성립하는가 / 서버가 관리할 시크릿이 늘어나는가
> — 이렇게 **우리 아키텍처와 연결된 기준**이라야 한다.

## 6. "결정" 이란 무엇인가

모든 작업에 이 스킬을 쓰는 게 아니다. **결정 축이 있는 작업**에만 쓴다.

### 결정으로 다룰 것

- 같은 목표를 이루는 **방식이 둘 이상 실재**한다
- 나중에 **바꾸는 비용이 크다** (API 스펙, DB 스키마, 외부 연동 프로토콜, 토큰 정책)
- 팀 컨벤션이나 관행에서 **벗어난다**

### 결정이 아닌 것

오타 수정, 포맷 정리, 리네이밍, 설정 파일 정리.

> **없던 고민을 지어내는 것이 이 스킬의 가장 큰 실패다.**
> 선택지가 없었던 작업은 `연관된 이슈` / `작업 내용` / `검증` 만 쓰고 끝낸다.

### 우리 도메인에서 결정이 나올 만한 곳

각자 맡은 부분에서 미리 감을 잡아두면 좋다.

| 도메인 | 갈릴 만한 지점 |
|---|---|
| 이미지 업로드 | 서버 경유 vs Presigned URL / 원본 보관 정책 / 리사이징 시점 |
| 타임캡슐 | 공개 시점 판정을 조회할 때 vs 스케줄러로 / 시간대 처리 |
| 알림 | 동기 vs 비동기 / 발송 실패 재시도 / FCM 토큰 관리 |
| 캘린더·기념일 | 반복 일정 저장 방식 (매 건 저장 vs 규칙 저장) |
| AI 서버 연동 | 동기 호출 vs 비동기 / 타임아웃·실패 처리 / 재시도 |
| 마이페이지 | 탈퇴 시 데이터 처리 (소프트 삭제 vs 하드 삭제 vs 익명화) |

**하나의 기능에 결정이 여러 개일 수 있다.** 카카오 로그인 하나에도
`카카오 인증 흐름` / `자체 토큰 전략` / `탈퇴 회원 처리` 가 각각 결정이었다.

결정 축이 3개를 넘으면 **중요한 1~2개만 깊게** 쓴다. 얕은 정리 5개보다 깊은 정리 1개가 낫다.

## 7. 실제 사례 — 카카오 로그인 (이슈 #1 → PR #4)

레포에 실물이 있으니 **꼭 한 번 읽어봐라.** 이 문서 열 번 읽는 것보다 낫다.

### 뽑아낸 것

**방식이 3개 있었다.**

- A. 백엔드 주도 인가 코드 방식 (서버가 리다이렉트까지 처리)
- B. 프론트가 인가 코드 수신 → 서버가 토큰 교환
- C. 프론트 SDK 가 액세스 토큰을 받아서 서버로 전달

**기준표로 갈랐다.**

| 기준 | A | B | C |
|---|---|---|---|
| 웹(React)에서 성립하는가 | ○ | ○ | **✕ SDK 가 토큰을 안 준다** |
| `CommonResponse` 규약 유지 | ✕ 리다이렉트로 토큰 전달 | ○ JSON | ○ JSON |
| 서버가 관리할 시크릿 | REST 키 + secret + redirect_uri | REST 키 + redirect_uri | 없음 |

**1행에서 C 가 탈락하고, 2행이 A 와 B 를 갈랐다.** → B 채택.

### 여기서 배울 점

1. **처음엔 C 로 구현했다가 B 로 갈아엎었다.** 카카오 JS SDK v2 가 클라이언트에 액세스 토큰을 주는 함수를 없앴다는 걸 뒤늦게 알았기 때문이다. **비교를 먼저 했으면 안 겪었을 일이다.** 이 스킬을 만든 이유가 정확히 이거다.

2. **포기한 것을 적었다.** "redirect_uri 를 프론트와 문자열까지 맞춰야 하고 환경마다 콘솔에 등록해야 한다." → 실제로 나중에 이것 때문에 시간을 썼다. **적어놨기 때문에 원인을 빨리 찾았다.**

3. **"⚠️ 짚고 갈 것" 이 실제로 일했다.** "닉네임 온보딩 엔드포인트가 아직 없어서 `isNewUser` 분기가 막다른 길이다" 를 미리 적어둬서, 다음 이슈가 뭔지 자동으로 정해졌다.

## 8. 자주 하는 실수

| 실수 | 왜 문제인가 | 대신 |
|---|---|---|
| 구현 다 하고 나서 `/git issue` | 이미 정한 걸 정당화하게 된다. 비교의 의미가 없다 | **코드 쓰기 전에** |
| "잘 모르겠어요" 라고 안 하고 대충 답함 | 근거 없는 문서가 나온다. 제일 나쁜 결과 | **모르면 모른다고 하면 조사해서 보여준다** |
| 일반론으로 기준 세우기 ("성능이 좋아서") | 우리 상황과 연결이 안 돼 판단 근거가 못 된다 | **우리 아키텍처·제약과 연결** |
| 단점 없다고 쓰기 | 단점 없는 선택은 없다. 없으면 애초에 결정 축이 아니었다 | **포기한 걸 구체적으로** |
| 오타 수정에도 억지로 비교표 | 없던 고민을 지어내는 것 | **결정 축 없으면 짧게 쓰고 끝** |
| 초안 안 읽고 바로 등록 | 네 이름으로 나가는 문서다 | **읽고 고치고 승인** |

## 9. 체크리스트

### 이슈 올리기 전

- [ ] 코드 쓰기 **전**인가
- [ ] 완료 기준이 검증 가능한 문장인가 ("~가 통과한다")
- [ ] 이번에 **안 할 것**을 적었는가
- [ ] 결정마다 대안의 장점을 먼저 인정했는가

### PR 올리기 전

- [ ] `./gradlew spotlessApply` 돌렸는가 (안 하면 CI 에서 떨어진다)
- [ ] `./gradlew build` 통과하는가
- [ ] 방식 비교표의 기준이 **우리 제약**에서 나왔는가
- [ ] **포기한 것**을 구체적으로 적었는가
- [ ] 이슈의 완료 기준을 실제로 만족했는가

## 10. 마지막으로

이 스킬은 **문서를 잘 쓰기 위한 도구가 아니다.**

구현 전에 한 번 멈춰서 **"방법이 이것 말고 또 뭐가 있지?"** 를 묻고,
**"내가 고른 것의 약점은 뭐지?"** 를 묻는 습관을 만들기 위한 장치다.

몇 번 하다 보면 스킬 없이도 그 질문이 먼저 떠오르게 된다. 그러면 성공이다.
그때부터 스킬은 **떠오른 생각을 기록으로 남기는 용도**로만 쓰면 된다.
